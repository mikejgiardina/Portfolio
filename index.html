Kymora

The physiological engine, the simulators built on it, and an iOS application that runs a Core ML surrogate of it on-device. One engine and three things that read from it, at three different stages of done.

Read this before the cards. Everything below is pre-1.0 and none of it is deployed against real patient data. ENGINE

Computational Physiology Engine

Evidence-Based Physiology, Computed in Real Time

Clinical Problem Every clinical tool downstream — simulators, training, decision support — needs a source of truth for how a body behaves over time. Off-the-shelf approaches don't give you a physiology you can compute, audit, and build on.

A physiologically grounded engine that computes a patient's trajectory from underlying mechanisms, cellular to system level. Vitals, labs, and drug response evolve over time, grounded in published physiology and pharmacology. Every case presentation is distinct, and the underlying state is fully auditable.

  • Multi-agent, physiologically grounded architecture
  • Physiology-driven behavior — not hard-coded scripts
  • GPU-accelerated batch computation
  • Evidence-based pharmacokinetic library
  • Clinical scoring: SOFA, qSOFA, NEWS2, GCS
  • Core ML surrogate export for on-device inference
  • Patent pending
Python PyTorch CUDA asyncio Core ML
SIMULATOR

Body Simulator

Clinical Simulator Front-End

Clinical Problem Bedside-quality patient simulators are locked into expensive vendor mannequins tied to a single training room. Every discipline that trains on patients needs a software-only simulator driven by real physiology, not scripted playback.

A clinical front-end wired live to the physiology engine over a WebSocket bridge. Vitals, four-channel waveforms, and drug response render from computed engine state in real time, with a graceful fallback when the bridge is offline.

  • Live WebSocket bridge to the engine
  • 4-channel waveforms: ECG, arterial, pleth, capno
  • Real-time vitals and pharmacological response
  • Code-split bundle for fast load
  • Graceful fallback when bridge unavailable
React TypeScript WebSocket Canvas

Simulated physiology for training and research. It does not display or interpret data from a real patient.

CONSUMER iOS

Meridian

Kymora — Consumer iOS Application

Consumer Problem Patients on complex medication regimens have no consumer-grade tool that pairs personal med tracking with a physiologically grounded model of how those drugs interact with their own biometrics.

Native iOS application pairing on-device medication tracking with a Core ML surrogate of our physiological simulation engine, so drug-context awareness runs locally, without sending biometric data to a server.

  • Native SwiftUI app targeting iOS 17+
  • HealthKit integration for biometric context
  • Core ML surrogate exported from the physiological engine
  • Local-first: on-device computation, privacy-preserving
  • Medication list organization and reminders, entered by label or barcode — no visual pill identification, which is ruled out by design
Swift SwiftUI HealthKit Core ML

ENGINEERING PRACTICE · LIVE · FIVE CASE STUDIES

How the Work Gets Built Safely

Automation, Enforcement, Disclosure Control, Parallel Sessions, and Clinical Evaluation Across a Multi-Repo Codebase

Engineering Problem A small team running daily AI coding sessions across several repositories has two exposures nobody else will catch: conventions that hold only while someone remembers them, and patentable mechanism sitting one paragraph away from every public draft. The layer that catches them has to work on everyone's machine, not just the one it was written on.

Five write-ups on the layer around the code. A lifecycle-hook layer that makes safety automatic; a register and ledger that convert remembered conventions into checks that go red; a staged pipeline that controls what leaves a patent-pending repo; an orchestration pattern for running several coding sessions at once without them colliding; and a measured evaluation of whether an AI review pipeline over a clinical corpus was reporting what it appeared to report. Each one documents where it has failed.

LIVE · ALL FIVE OPEN NOW
  • Lifecycle hooks across every stage of a session, on three operating systems
  • Fail-open by default, fail-closed where a false pass is unrecoverable — and never fail-silent
  • Every discipline classified enforced, narrated, or hybrid — and tracked
  • A hard bar before a check may be called "enforced"
  • Checks that turned out never to fire — found, fixed, published
  • A staged disclosure pipeline, weighted by audience, gaps named
  • Parallel coding sessions leased by write-surface, with every serial resource routed through one writer

CLINICAL PRODUCT · LIVE · OPEN SOURCE

Trauma Tracker

A Real-Time ED Trauma Registrar

Clinical Problem A trauma resuscitation generates an enormous amount of documentable fact in a very short window, and everyone in the room is busy. The record gets reconstructed afterward, from memory, by someone who was also running the resuscitation — which is where timestamps drift, quality measures get missed, and charges go unsupported.

Multi-agent documentation that runs during the resuscitation rather than after it, producing the nursing narrative, the accreditation clocks and the charge capture from one set of timestamped events. Anything it asked about and did not get an answer to rides through to the report as a documented gap rather than being resolved away.

LIVE · RUNS IN THE BROWSER
  • Values and interventions extracted and stamped as they are spoken
  • Shock Index, RTS and GCS computed deterministically from published tables — not inferred
  • A charge fires only when the documentation that code requires is actually present
  • Activation determination carries the evidence it was made on
  • Unresolved prompts appear in the output as documented gaps
  • Four capture sources · synthetic data only
