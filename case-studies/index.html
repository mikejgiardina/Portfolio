FIVE WRITE-UPS · REVISED AS THE SYSTEM CHANGES

Engineering practice

The layer around the code.

Most of what keeps a codebase correct isn't in the codebase. It's in what runs automatically, what gets checked rather than remembered, and what is allowed to leave the repository at all.

These are five write-ups on that layer, built for a multi-repository system where AI coding sessions run daily across several machines and more than one contributor, and where most of the working knowledge still sits with one person. Each one names the incident that produced the rule, and each one documents where it has failed.

python simulation engine · typescript / react apps · swift ios app · markdown docs corpus · agent-config repo

01 · Automation
Giving a workspace a nervous system
lifecycle hooks

Small, portable scripts that fire at fixed moments in every session to enforce safety, quality, and workflow — backed by command, skill, scheduled, and review-agent layers. Most only advise. The ones that can stop a command are the interesting decision, and they don't all stop it for the same reason.

Read the case study →
02 · Enforcement
Checks that outlive the author
narrated → enforced

A process document that works because its author keeps re-reading it is a journal. Every discipline gets sorted into checked or remembered, with a scoreboard for moving items between the two — a hard bar before anything earns the word, and a running list of the checks that turned out not to fire.

Read the case study →
03 · Disclosure
Publishing out of a patent-pending codebase
disclosure control

Public writing drafted inside private repositories that hold patentable mechanism. A staged pipeline between a draft and a published file, weighted by where it's going — plus every place it has failed, and the gap still open.

Read the case study →
04 · Clinical evaluation
Two reviewers agreed. That was the problem.
evaluating the evaluator

Two AI reviewer personas over a clinical-education corpus, keeping only what both of them flag. Then measuring whether that agreement meant anything: it had promoted a shared blind spot to top confidence, most blockers turned out to be missing source material, and the gate was checking that review had happened rather than that anything got resolved. Sixteen real clinical defects were behind it, several of them dosing.

Read the case study →
05 · Orchestration
One coordinator, several workers — and an error rate for all of it
parallel sessions

Twenty-eight rounds of running AI coding sessions concurrently against one shared repository set. The architecture — partition by write-surface, route everything serial through a single writer — is the ordinary part. The distinctive part is running an error-rate instrument on the whole thing: an admission rule that moved the measured rate ten-fold without the work changing, a headline figure wrong by one because the graded party was the grader, and 100% inter-rater agreement published together with the reason to discount it.

Read the case study →

The code behind the first two is open. github.com/mikejgiardina/hook-discipline — the hooks, the three-state exit contract, and the paired fire-and-control suite, Apache-2.0. And if you would rather read a clinical product than a process write-up, Trauma Tracker is a real-time ED trauma registrar, public and running.

They're written to be read in any order, though they run in roughly that one: the first is the layer that runs, the second and third are the layer that decides, the fourth asks whether any of it was actually working, and the fifth is what happens when several sessions use all of it at once. Process shape only — proprietary specifics are generalized or omitted throughout.
