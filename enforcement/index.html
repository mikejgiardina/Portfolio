ENGINEERING CASE STUDY
PROCESS · KEY-MAN RISK

Process design · governance

Turning conventions into checks that outlive the author.

A process document that only works because the person who wrote it keeps re-reading it isn't risk mitigation — it's a journal. A process enforced by a failing check survives that person leaving. So I sorted every discipline this workspace runs on into those two piles on purpose, and built a scoreboard for moving items from one pile to the other. When the scoreboard shrinks, key-man risk shrinks — measurably, not rhetorically.

solo founder-engineer · a decision-record corpus · a set of living process documents

Two artifacts do the work. A register maps every discipline and classifies it. A ledger tracks the conversion work and verifies that the ones already claimed as enforced actually fire. The register is the map; the ledger is the scoreboard. They're separate because a backlog buried inside a reference document stops being a backlog.

Totals are deliberately absent from this page. The only figure worth quoting is a direction — how much of the operating layer has moved from remembered to checked — and a level quoted on a permanent page goes stale on its own, which is the precise failure the whole exercise is about.

01

The two columns most registers leave out

Plenty of projects keep an index of their process docs. It answers “what governs us, and where does it live.” That's useful and it isn't enough, so the register adds four columns.

column

Forged by

The specific incident that produced this rule. Every entry names one. A procedure with no incident behind it is process theater, and it's the first thing a successor ignores.

column

Enforcement

Enforced, narrated, or hybrid. The gap between the enforced pile and the narrated pile is the key-man risk, written down where it can be watched shrinking.

column

Owner on handoff

Who owns this when I'm not the one running it. Today most rows say “founder.” Naming the role that inherits each one makes the handoff a delegation exercise instead of an excavation.

discipline

Point, never copy

The register classifies and links; it never holds a procedure's body. If a procedure's content starts getting pasted in, that's the signal to stop and link instead — a rule with two homes has already begun to drift.

The stranger-trap tier. The register also catalogues rules that live as prose inside configuration and context files, never extracted into a standalone document — the ones a newcomer misses completely. They're indexed here so they're findable, and left where they are, because that's where they're enforced. It tracks procedures that don't exist yet as well, each with the event that would earn one.

02

Three states, and a caveat

Every discipline gets exactly one value. A generous classification is worse than none, so the definitions are strict.

StateMeansSurvives the author leaving?
ENFORCED A test, audit, hook, or CI gate goes red when the procedure is violated. Yes.
HYBRID Part is checked; part rides on a human reading the prose. Partly — the narrated half doesn't.
NARRATED Prose. Often correct, often battle-forged, but it holds only while someone reads it. No.

The caveat printed at the top of the column. These values reflect what the source documents claim is enforced. Until a row has been walked — a live check shown to go red rather than silently pass — it reads “claimed enforced, verify it bites.”

03

What earns the word “enforced”

All four have to be true, because a check that silently passes is worse than no check at all.

It fails red on a real violation

Proven with a known-bad fixture, not assumed from reading the code. If you can't show it failing, it isn't a check yet — it's an intention with a filename.

It does not pass green on a degraded environment

A cold virtual environment, a missing dependency, an absent file: all must produce an explicit error, never a silent pass. The reference pattern resolves through a chain of fallbacks and, when it runs out, degrades to “no result” rather than to a wrong one.

It runs automatically

A CI gate, a session lifecycle hook, or a pre-publish step — not “remember to run it.” A check that depends on being remembered has the same failure mode as the convention it replaced.

Its failure message points at the fix

A red check that doesn't say what to do hasn't removed the tacit knowledge from the founder's head. It has relocated it into a stack trace, where it's harder to find.

Criterion two came from a real incident: an audit's last-resort fallback fired on a cold environment and manufactured a regression of over a thousand findings that did not exist. Nothing was broken except the ability to tell. Degrade-to-nothing beats degrade-to-plausible.

04

Three ledgers

The scoreboard splits three ways, because “not yet enforced,” “claims to be enforced,” and “can never be enforced” need three different kinds of attention.

AConversion backlognarrated → target check

The work, ordered by leverage. Each row names the concrete check to build, where it will live, what it must assert, and what it costs to keep not having it. Highest-leverage items are the ones with direct external exposure — anything that could put a wrong number in front of a grant reviewer or an investor.

Rows are honest about partiality. Several are marked “backlog (partial)” because only the mechanical portion of the discipline can be checked and a judgment residue will always remain. Pretending otherwise would produce a check that passes while the actual rule is broken.

BVerification queueclaimed-enforced → prove it bites

Every check that says it's enforced, with two separate columns: exists (the file is on disk) and bite-tested (a known-bad input has been shown to make it go red). Until the second column is filled in, the check is provisional no matter how good the code looks.

This queue is why the register carries that caveat. The first pass through it found two. No pass since has come back empty.

CWon't enforcejudgment · stop trying

Disciplines that are irreducibly judgment: how to collaborate with an agent, when a change deserves a decision record, whether a given commit is a release, the order to work through a triage. These stay narrated; their mitigation is onboarding and documentation, not a gate.

Writing them down as permanently unenforceable stops effort being spent trying, and keeps the ledger from carrying items that will never close.

Open gap: the map drifted. The ledger gets touched every time a check moves, so it stays current by construction. The register doesn't — nothing forces a visit — and it fell roughly two months behind the layer it classifies while that layer was being worked on heavily. It now understates coverage, which is the benign direction and is not the point: the artifact whose job is tracking drift drifted, and nothing noticed. The fix isn't diligence, it's the same move as everywhere else on this page — a check asserting the map is not more than N days behind the scoreboard. Until that exists, this is a narrated rule about a document full of narrated rules.

05

What the walks found

The verification queue was built on a suspicion: that some checks the register listed as enforced weren't firing. The first walk confirmed it twice. Both had been reporting success.

casualty one · failed to warn

The scanner that examined nothing

A protective scanner read the path of the edited file from environment variables the runtime no longer provided. The path came back empty, so it exited on its first line — every run, silently. Its warning was also written to a stream the wiring discarded, so even when it did have something to say, nobody heard it. Two independent bugs, stacked, both quiet.

The register had it as enforced. It was found by accident, while a neighbouring script was being edited — not by any check.

The fix was also wrong, and that took seven more weeks to notice. The diagnosis was right — the variable didn't exist — and the correction reached for a second variable that didn't exist either. Identical symptom, now with a commit message claiming it was resolved. Everything built on top of that scanner in the interim was built on nothing. A fix verified by reading is not verified.

casualty two · allowed what it blocked

The gate that depended on a tool that wasn't installed

A commit gate — the one whose whole job is to refuse a commit that stages a credential — used a JSON command-line utility for both reading its input and emitting its decision. That utility isn't installed on the machine in question, deliberately. Its wiring swallowed errors so a broken hook could never block real work. Net effect: the gate errored before it evaluated a single commit — one staging a real credential would have passed indistinguishably from a clean one.

Two further latent bugs surfaced during the fix: the denial used a message format the runtime had superseded, and the scan ran from a working directory that wasn't the repository being committed to — so even with the tool present, it would have inspected nothing.

How this surfaced changes what it is: no credential ever leaked. The gap was found by walking the queue on purpose and feeding the gate a crafted bad input — the proactive path, before anything exercised it in anger — and it was closed the same day. That is the queue doing its job, not an incident report.

That one failed to warn; this one silently allowed. It was wired but never registered in either artifact, so it read as neither enforced nor tracked. The rewrite inverted its posture: any commit-shaped command it cannot evaluate — interpreter missing, interpreter crashing, target unresolved — now denies. Then it was re-tested twice: once against crafted inputs, once live through the real wiring, including a simulated broken toolchain that the old version waved through.

Two softer findings landed in the same pass, both “the map said enforced, the territory disagreed”: one check was a reminder mislabeled as a gate (the rule it supposedly enforced was narrated all along), and another was present on disk but never wired to any event, so it had never once run. Neither was a fail-open, but both were corrected in the register, because an overclaimed check is a lie about coverage even when the code is fine.

casualty three · the verifier had the bug

A suite where every passing test proved nothing

Both casualties above were found by luck, so the queue stopped being walked by hand and started being walked by a regression suite — a test file per hook, each one asserting the hook fires on a known-bad input and stays quiet on a control.

The first run of one of those files came back twelve passing, twelve failing. The twelve passes were every “no write occurred” case — and they passed because the stubbed-out command was never reached at all: the test harness had been talking to the live production board the entire time. It was recording real successes as proof that nothing had happened. Only the paired control caught it, because the assertion that something is absent is satisfied perfectly by a test that never ran.

The cause was a platform detail with no relationship to the check being tested: the native process launcher appends one specific extension to an extensionless command name and ignores the rest, so both forms of the stub were skipped and the real tool resolved instead. The verification layer had exactly the property it was built to detect in the layer beneath it — and it caught its own author twice in one sitting, on malformed fixtures that produced clean exits and zero output, indistinguishable from a hook that was genuinely dead.

Which is now the standing rule for the suite: every fire case is paired with a control. Most of these hooks are advisory, so silence is their success case — and an all-quiet suite is also precisely what a dead hook produces. Without the control, a green run is not evidence of anything.

casualty four · the opposite failure, and it is worse in one way

A guard that fired on a clean tree

Every casualty above is a check that stayed quiet when it should have spoken. This one is the mirror image. A line-ending guard reported that every script in the tree contained a carriage return — in a tree that contained none.

The cause is a platform-specific quirk of the tool doing the matching: in recursive list-only mode it named every file as matching, while asking the same tool to print the matching lines in any one of those files returned nothing. Two invocations of one utility, disagreeing about the same file, on one platform only.

A guard that fires on a clean tree is uninformative in exactly the way a guard that never fires is uninformative — and it is worse in one respect, because it actively teaches its reader to ignore the channel. That is the same alert-fatigue argument that governs which of these hooks are allowed to block, arriving from the other direction.

the counter-example · an assertion added for no reason, which paid immediately

Six failures all pointing away from the fault

An assertion was added to a fixture defensively — not to catch a known defect, just because the value it checked had never been checked. It earned its place on the next run.

Six assertions across three unrelated blocks were failing, all of them reporting that a hook had stopped warning. Every one pointed at the hook. The new assertion collapsed all six into a single fatal error naming the file that was never written and the interpreter that failed to write it.

The six were not wrong. They were downstream, and downstream failures describe the symptom in the vocabulary of wherever they happen to sit. The useful assertion is the one closest to the thing that actually broke — and you generally cannot know in advance which one that is, which is the argument for adding it when you have no reason to.

That sweep found five further defects. None was fixed in the same pass, because changing a hook's behavior sits behind a confirmation gate that adding a test deliberately does not — so each was filed instead, and carried as a self-converting known-gap test: an assertion of the current, wrong behavior that goes red the moment someone fixes it, with the instruction to convert it and close the item written into the failure message. A defect you've decided not to fix yet is still worth pinning down, and this keeps the backlog honest without letting the suite lie about what's working.

The rule that came out of it. A wired hook is not a tracked check, a tracked check is not a biting one, and a passing test is not a check that ran — each gap closes only from the outside, by something that assumes the layer beneath it is lying. The corollary is scheduling: the first two casualties were caught reactively, by luck. The proactive complement is deliberately not a one-session sprint — a few rows driven to bite-tested per session, reviewed at every release, plus a recurring sweep that files what it finds where the work actually is. The queue's job is to keep the residual visible in the meantime, and it says out loud which proofs are still owed.

Why a solo founder builds this

Because the risk that matters isn't a bug. It's that the working knowledge of how a multi-repository system stays correct lives in one person's head, and every convention that survives only by being remembered is a piece of that exposure. Converting a remembered rule into a red check is the only move that reduces it permanently — and unlike documentation, it can be counted.

Which is why the ledger is a separate artifact rather than a section. Ledger A shrinking, and Ledger B graduating to bite-tested, is the literal measure of how much of this operating layer now survives the author leaving. It's the only process metric here that can go the wrong way and show it.
