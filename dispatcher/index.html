COORDINATING PARALLEL AI SESSIONS
IN USE SINCE OCTOBER 2026
A WAY OF WORKING · NOT A PRODUCT

Field notes · the current approach

One coordinator, focused lanes.

From August to mid-October 2026 I coordinated several AI coding sessions at once through a heavy protocol: numbered rounds, a ledger of which session could write which files, a sealed record per round, and a separate session that graded the coordinator's mistakes against a written rubric. That record is archived here.

In October 2026 I retired it for something much lighter. Much of its cost was ceremony that existed only to run the protocol itself, paid on every round however small, and some of the rest the tools now supply. This page is what replaced it, and the two measurements I kept.

The figures come from the archived protocol's own round ledger, kept by the sessions as they worked. Nothing here is a product, and nothing here describes the content of the work the sessions did.

01

The model

One session holds the queue. Every other session does one thing.

One coordinator

A single coordinating session holds the queue of tracked work, decides the order, writes a brief for each item, and starts a separate session for it. It is the only session that writes to shared files: the tracking board, shared indexes, change logs.

Focused lanes

Each lane is one tracked item, in its own isolated copy of the repository, with a list of the files it may change. Two lanes never hold the same files. Where two items need the same file, they run one after the other.

Verify before anything is recorded

A lane reporting "done" is making a claim. Before anything durable happens, the coordinator checks the change against the brief, and after each merge it confirms the merged content contains every file the change listed. A merge here has once reported success while landing nothing.

Decisions as pre-approvals

When I decide something, the decision is written on the tracked item as a dated comment naming the option I chose. Work that implements that decision does not come back to me for approval. Anything outside it does. The checks still run; the pre-approval removes the wait, not the review.

One queue for the heavy test run

The full local test run takes more than half an hour, and one machine can run one at a time. Lanes now queue for it themselves, first come first served, instead of waiting for the coordinator to schedule them.

A separate reader, on demand

For anything that leaves the private repositories, including this page, a separate reviewer session reads the finished piece without the reasoning that produced it. In the old protocol that reader ran every round. Now it runs where a claim is going outward.

None of this is new as a pattern. A dispatcher with a queue, workers with disjoint assignments and a check at the merge is how a lot of work has been organized for a long time. The specific thing about AI sessions is that they cannot negotiate with each other: two people who need the same file talk first, and two sessions both write it.

02

Why the heavier protocol went

Its fixed cost only paid off with many sessions, and the late rounds had few.

The old protocol ran forty-one rounds between August and mid-October 2026. Every round carried the same overhead whatever its size: changes that opened, recorded and closed the round itself, a ledger of file claims, a seal, and a grading session. That overhead earns its keep when many sessions run at once. In the late rounds, one to three did.

The other half of the reason is the tools. Part of the protocol was scaffolding for things the tools have since improved: scripted multi-agent runs (the Workflow tool, Claude Code v2.1.269, September 2026), subagents that run in the background by default (v2.1.302, October 2026), and, in the desktop app, one session starting others that report back to it. What the tools still do not provide, and what I kept, are the rules in section 01 and the measurements below.

The lighter model has been in use for days. I have no measurement of whether it is better, and this page does not claim one.

03

Separately graded errors

The party that made a mistake may record it, and may not grade it.

From round 32 the coordinator stopped scoring its own mistakes. Any session could record an entry, including against itself. A separate grading session started only after the round was sealed, read the sealed record (and, where an entry needed it, the source documents), and classified the entries against a written, versioned rubric. how to read it

This is a series, not a trend. Six rubric versions are in force across these ten rounds, and the number of work sessions per round ranges from five down to one.

A fall from 40 to single digits mixes three things: what counted as an error, how much work each round did, and whether the work got better. The table cannot separate them, so I do not claim it improved. Counts are only compared within one rubric version. Several figures were revised when a later grader carried an entry forward, and the earlier value stays beside the revision in the record.

The final round shows how the grading was checked. The grader wrote down its own classification and fixed it with a hash before a second, blind reader saw the five entries, stripped of anyone's proposed answer. They agreed on all five. The grader then read the underlying sources and changed one entry, which lowered the count from four to three. Because the change moved the count, it was sent to me to rule on. Both results are recorded. The gap between them marks the one entry whose meaning the record alone did not carry, which is what a blind reading is for.

How often I am needed

The quantity I am trying to change, and the one I can least afford to estimate.

The point of more automation is to need me less often. The old protocol counted the decisions I had to make in each round.

Round32333435363738394041
Decisions I made969151011141176

Round 35 reads 16 when it is re-derived from the decision records rather than taken from the round's own summary. Both values stay in the record.

These are counts per round, and rounds ran from a few hours to several days, so they are not a rate. The measure I want is the time between decisions. Under the current model every decision is a dated comment on the item it concerns, which makes the interval derivable from the records instead of reconstructed afterwards. The log that reads them is being moved over from the old round records now. There is no interval figure yet, and this page does not estimate one.

05

What this does not show

It does not show time saved. How long this work would have taken a person, or the old protocol, was never measured, and I am not going to estimate it. It does not show that the software these sessions worked on is any good; that is judged elsewhere, against its own evidence. And the error series above is not evidence that anything improved.

What it shows is a working arrangement with its measurements attached: who is allowed to grade whom, what was counted, under which rubric, and where the numbers stop.

I specified how this should run, and AI coding sessions built and ran the tooling for it. I did not write the code and do not claim to.
